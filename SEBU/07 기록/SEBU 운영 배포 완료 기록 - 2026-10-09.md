# SEBU 운영 배포 완료 기록 - 2026-10-09

**SEBU 운영 서버·HTTPS·첫 배포·전체 연구 정보 이관·Pull 자동 배포·S3 백업 복원 검증은 완료됐다.** 공개 화면의 `/api`도 운영 API에 연결돼 있다. 실제 학교 로그인, 기존 로그인 쿠키 전환, 북마크·프로필·후기 쓰기의 브라우저 수용 검증은 FE 담당자에게 남아 있다. 공개 HTTP 성공을 전체 사용자 기능 검증으로 확대하지 않는다.

이 기록은 2026-10-08의 3~7단계 완료 기록과 공개 HTTP 검증 결과를 대조하고, 10월 9일 코드 기준과 운영 핫픽스 결과를 연결한 것이다. 명령 스크립트의 존재가 아니라 성공 결과·대조값·제약을 근거로 완료 범위를 정했다. 이번 지식 갱신에서 AWS 리소스를 새로 조회하거나 배포하지 않았고, 비밀값·환경 파일·DB 원문·회원 내용은 옮기지 않았다. 1~2단계는 [[SEBU 운영 준비 검증 기록 - 2026-10-08]]을 참고한다.

## 현재 구조와 합의

| 구분 | 확인한 구성과 운영 원칙 |
|---|---|
| AWS | CLI 프로필 `sebu`, 선택 리전 `ap-southeast-2`. Toolkit 접속 리전과 배포 리전을 구분 |
| BE 브랜치 | `main` 운영, `develop` 개발. 검증된 변경을 운영에 반영하고 핫픽스는 양쪽 코드에 유지 |
| FE 브랜치 | `dev`가 운영 배포 브랜치. FE 구현·배포·기능 검사는 FE 담당자 소관 |
| 사용자 주소 | `https://www.sebu.kr`; 상대 `/api/:path*`를 `https://api.sebu.kr/api/:path*`로 전달 |
| 기존 FE 주소 | 현재 `vercel.json`은 `sebu-frontend.vercel.app`의 비 API 페이지를 `www.sebu.kr`로 영구 리다이렉트 |
| 개발 서버 | 필요할 때만 켜는 방식. 주 1회 약 2시간은 사용 예상이며 자동 기동·중지 예약 완료 기록이 아님 |
| 배포 방식 | GitHub Actions의 비공개 GHCR 이미지 → 운영 EC2 Pull → 단일 컨테이너 교체. 블루그린 구성 없음 |
| 진행·브라우저 | 운영 변경은 단계별 결과 보고 후 다음 지시를 기다림. 브라우저 작업은 URL·구체적 프롬프트를 전달해 사용자가 Aside AI로 진행 |

## 3단계 — 운영 기반과 HTTPS

별도 운영 EC2·MySQL·Caddy를 구성했다. 운영 서버는 `t3.small`, 암호화한 30 GiB gp3, 표준 CPU 크레딧 모드다. 외부 TCP 포트는 80·443이며 IMDSv2 필수, 종료 보호, 볼륨의 종료 시 보존을 설정했다. 재부팅 후 MySQL 영속성·고정 IP·비밀 파일 보존을 확인했다.

DNS와 기본 TLS 신뢰를 사용하는 외부 접속으로 `api.sebu.kr` 인증서와 HTTP→HTTPS 308 전환을 확인했다. 이 단계의 HTTPS 503은 백엔드를 아직 배포하지 않은 준비 응답이었다. 이를 애플리케이션 배포 성공으로 기록하지 않았다.

비용은 10월 8일 마지막 확인 시 FREE·ACTIVE, 잔여 크레딧 USD 72.86, 만료 2027-03-06 14:19 KST였다. 유료 플랜으로 전환하지 않았다. 당시 운영 기본 추정 월 USD 25.802는 730시간의 EC2·공인 IPv4와 30 GiB gp3 기준이며 백업·초과 트래픽·세금은 제외한다. 현재 비용이나 잔액을 보증하는 수치가 아니므로 추가 운영 선택 때 다시 확인한다.

## 4단계 — main 출시와 첫 배포

[BE PR #95](https://github.com/greedy-team/SEBU-backend/pull/95)를 머지해 `main`의 첫 운영 릴리스 `f0d355316041ce334f7bec4beb155e838538396a`를 만들었다. [main CI](https://github.com/greedy-team/SEBU-backend/actions/runs/37748066938)의 테스트와 이미지 게시 성공, 검토한 develop과 main의 트리 일치, 게시한 정확한 digest의 실제 배포를 확인했다.

운영 DB에 V1~V49를 적용해 기본 교수·연구실 각 321개를 생성했고, 제외 대상 12개 활동·후보 테이블은 0건이었다. 백엔드·MySQL은 healthy, Caddy는 실행 상태였고 공개 연구실·단과대·카테고리 API는 200, 비로그인 `/me`는 401이었다. 실제 DNS·TLS와 운영 출처 CORS도 확인했다. 이때 Pull 도구는 설치·점검했지만 이관 전이므로 타이머를 아직 켜지 않았다.

## 5단계 — 전체 연구 정보 이관과 Pull 배포 활성화

개발 연구 정보의 최신 스냅샷을 AWS 내부에서 운영으로 전달해 아래 11개 테이블을 복원했다. 교수·연구실 각 321개인 기본 자료를 각 622개의 전체 자료로 맞췄고, 모든 이관 테이블의 전체 일반 컬럼 해시가 일치했다. 스냅샷 원문은 AWS 밖으로 내려받지 않았다. 임시 전달 서비스·네트워크 규칙·개인 키는 작업 뒤 제거했다.

| 테이블 | 이관 확인 행 수 |
|---|---:|
| `college` | 9 |
| `department` | 64 |
| `crawl_source` | 55 |
| `professor` | 622 |
| `laboratory` | 622 |
| `professor_department` | 666 |
| `laboratory_department` | 666 |
| `research_field` | 1,899 |
| `laboratory_research_field` | 2,134 |
| `research_field_category` | 54 |
| `research_field_category_mapping` | 2,210 |

회원·토큰·북마크·게시글·댓글·후기·크롤링 후보 등 제외 12개 테이블은 **이관 직후 모두 0건**이었다. 이후 사용자 활동으로 값이 늘어날 수 있으므로 현재 운영 DB의 상시 불변 조건으로 사용하지 않는다. 실제로 10월 9일 핫픽스 검증 때는 기존 후기가 보존되는지를 확인했다.

외부 공개 검사 17개가 모두 통과했다. 연구실 622개, 단과대 9개, 카테고리 54개와 하위 20개, 연구실 상세·카테고리 참조·후기 정렬 페이지와 인증 경계를 확인했다. 대표 소속 기준 자연과학대 54개, 생명과학대 59개, 인공지능융합대 207개도 대조했다. 실제 학교 로그인과 쓰기는 이 검사에 포함하지 않았다.

이관과 앱 상태 확인 후 `main` Pull 타이머를 enabled·active로 만들고 첫 서비스 실행 성공을 확인했다. 약 2분마다 새 이미지 digest를 확인하는 단일 컨테이너 교체 방식이며 짧은 중단이 생길 수 있다. SQL 지문이 바뀐 배포 실패는 코드·DB를 자동 원복하지 않으므로 수동 확인이 필요하다.

## 6단계 — 전체 백업·S3 분리 보관·실제 복원

사용자 승인에 따라 운영 전체 DB의 초기 기준 백업과 S3 분리 보관을 구성했다. 로컬 기준 백업 복원에 이어 S3의 **정확한 객체 버전**을 AWS 내부로 가져와 임시 DB에 복원했다. 두 경우의 핵심 확인은 다음과 같다.

- 24개 전체 테이블의 원본·복원 결과 일치와 35개 외래 키 관계를 검증했다.
- 운영 원본이 바뀌지 않았고, 임시 복원용 사용자에게 운영 DB 접근이 거부됨을 확인했다.
- 검증 뒤 임시 DB·사용자를 제거했다. 실제 SQL 덤프는 지식 저장소나 로컬 자료로 내려받지 않았다.
- 백업·S3 전달 도구의 단위 테스트 26개와 실제 업로드·검증을 확인했다. 이 운영 전용 도구의 서버 설치본은 백엔드 저장소의 `source_ids`만으로 복구할 수 있는 범위와 구분한다.

| 항목 | 설정·확인 결과 |
|---|---|
| 정기 백업 | 매일 03:00 KST, persistent systemd 타이머 활성화 |
| 실제 실행 | 같은 서비스의 첫 수동 실행 성공과 S3 업로드 확인. 이후 예약 시각의 자동 실행 결과는 미확인 |
| 재시도 | 실패 시 5분 간격, 시간당 최대 3회 시작 |
| 로컬 일일 보존 | 검증된 최신 백업·manifest 7쌍 |
| S3 일일 보존 | 7일 후 만료, 비현재 버전 1일 후 만료. 수명 주기 처리는 비동기 |
| 초기 기준 백업 | 자동 만료 없음 |
| 접근 로그 | 별도 버킷·7일 만료 구성. 실제 로그 객체 도착은 미확인 |
| 보호 설정 | 비공개, BucketOwnerEnforced, 버전 관리, SSE-S3, HTTPS 전용, SSE-C 차단 |
| 접근 권한 | EC2 역할의 지정 baseline·daily 경로에 PutObject·GetObject·GetObjectVersion. 정적 액세스 키 사용 없음 |

백업 실패의 외부 이메일·채팅 알림은 설정하지 않았다. systemd 결과와 비공개 상태 파일로 진단하며, 예약 실행의 지속 성공·S3 접근 로그 도착은 후속 운영 점검 대상이다.

## 7단계 — FE 운영 연결과 검증 경계

FE의 `/api` 목적지는 운영 API로 변경됐다. 초기 세션 전환 대응 변경 [FE PR #176](https://github.com/greedy-team/SEBU-frontend/pull/176)은 사용자 요청으로 [PR #177](https://github.com/greedy-team/SEBU-frontend/pull/177)에서 되돌렸고, 되돌림의 Vercel 배포 성공을 확인했다. 이 임시 변경의 재시도·세션 보호 기능과 당시 테스트 결과를 현행 FE 구현으로 남기지 않는다. FE 담당자의 동시 변경과 로컬 변경은 보존했다.

이후 10월 8일 21:01 KST의 인증 없는 GET 점검에서 `www.sebu.kr/api`와 `api.sebu.kr/api`의 연구실·단과대·카테고리 응답은 각각 200과 같은 JSON 지문이었다. 연구실 622개·단과대 9개·카테고리 54개를 확인했다. 양쪽 `/me`는 쿠키 없는 요청에 401 `ACCESS_TOKEN_INVALID`였고, 홈·검색·단과대·로그인·마이페이지 URL은 SPA HTML을 200으로 반환했다. SPA HTML 제공을 로그인이나 화면 상호작용 성공으로 해석하지 않는다.

현재 FE `dev` 기준 `e7e54de`에는 운영 API rewrite와 기존 Vercel 주소의 비 API 페이지 리다이렉트가 있다. 실제 인증 세션 검사는 FE 담당자가 진행하며, 별도 FE 변경 요청 없이는 FE 코드 수정·커밋·PR·머지를 진행하지 않는 합의를 유지한다.

## 10월 9일 후속 운영 반영

BE PR #96·#97로 물리천문학과 누락 링크를 보완하는 V50을 운영·개발 코드에 반영했다. [main CI·이미지 게시](https://github.com/greedy-team/SEBU-backend/actions/runs/37887826434)와 [develop CI·이미지 게시](https://github.com/greedy-team/SEBU-backend/actions/runs/37887953157)가 성공했고, 운영의 기존 Pull 배포를 통해 반영됐다.

운영 API와 서비스 API에서 새 URL 14개 일치, 나머지 URL 15개 유지, 전체 연구실 622개·물리천문학과 29개 유지, 김경호 교수 연구실의 기존 후기 1개 보존을 확인했다. Aside AI의 실제 상세 화면에서도 지정 링크 표시를 확인했다. 개발 이미지 게시 성공은 개발 DB 적용 성공과 다르며, 이 작업을 위해 개발 서버를 별도로 시작하지 않았다.

## 남은 확인

- FE 담당자: 새 세션·기존 로그인 세션의 실제 학교 로그인, 새로고침·만료·로그아웃·CSRF와 북마크·프로필·후기 작성 흐름.
- 운영 담당자: 다음 예약 백업 실행과 S3 업로드의 지속 성공, S3 접근 로그 도착, 모니터링 수집 연결과 외부 실패 알림의 필요 여부.
- 개발 재개 시: 서버 상태·비용 재확인, 최신 develop 이미지 배포와 DB 마이그레이션 적용 확인. 주간 자동 기동·중지 설정 여부는 별도 결정.
