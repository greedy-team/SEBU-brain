# SEBU 운영 준비 검증 기록 - 2026-10-08

> 이 문서는 1~2단계 종료 당시 기록이다. 이후 실제 운영 전환·백업 결과는 [[SEBU 운영 배포 완료 기록 - 2026-10-09]]에 이어서 기록했다.

**운영 배포 채널과 연구 정보 이관 코드를 준비하고 격리 DB에서 검증했다. 실제 운영 서버·DB 생성과 운영 전환은 하지 않았다.** [백엔드 PR #94](https://github.com/greedy-team/SEBU-backend/pull/94)의 구현을 [[SEBU 운영 전환과 연구 정보 이관]]에 정리했다. 이 문서는 실행 결과와 미완료 범위를 구분한다.

[PR #94](https://github.com/greedy-team/SEBU-backend/pull/94)는 2026-10-08 14:09 KST에 develop으로 머지됐다. 기준은 [d1010d4](https://github.com/greedy-team/SEBU-backend/commit/d1010d405abfcb5f9b01b155c48032da01ee1d2d)이며 main 출시와 실제 운영 배포는 아직이다.

## 1단계: 비용과 구성 확인

10월 8일 AWS 조회에서 FREE 플랜과 잔여 크레딧 **$73.07**, 플랜 만료일 **2027-03-06 14:19 KST**를 확인했다. 이 값은 당시 조회 기록이며 현재 잔액을 보증하지 않는다. 실제 리소스를 만들기 전 다시 확인한다.

선택한 구성은 같은 프로젝트·`ap-southeast-2`의 별도 운영 EC2 `t3.small`과 30GB gp3, 한 EC2 안의 백엔드·MySQL·Caddy다. 개발은 필요 시 주 약 2시간, 운영은 상시 사용한다. 정지한 EC2의 EBS 비용은 남고 영구 무료 구성은 아니다. 운영 EC2는 이 단계에서 생성하지 않았다.

## 2단계: 코드와 자동 검증

- `develop`·`main` 채널을 구분하는 이미지 게시·Pull 설정과 각 환경 예시를 작성했다. 운영 DB/JWT 비밀값과 실제 API 주소는 입력 전이다.
- MySQL 8.0에서 SQL·Java를 포함한 마이그레이션 49개를 적용하고 Hibernate 검증, 공개 API, 운영 도메인 CORS를 확인했다.
- [검증 커밋 43f5d82](https://github.com/greedy-team/SEBU-backend/commit/43f5d82ccde16f98722f4cd5f66f1af3eaa09326)의 [GitHub CI](https://github.com/greedy-team/SEBU-backend/actions/runs/37728649536)가 통과했다. 배포·이관 Python 단위 테스트는 60개다.
- CI는 **합성한 테스트 자료**로 catalogue 이관 후 앱/Hibernate/API 검증과 실패 복구 경계를 검사한다. 실제 개발 DB 원문을 GitHub Actions에 업로드하지 않았다.
- 로컬에서는 빌드에 성공했지만 Java 테스트 클래스 로딩과 Docker 엔진에 환경 문제가 있어, 로컬 전체 앱 테스트 성공으로 기록하지 않는다. 전체 Java·실제 MySQL 자동 검증의 근거는 위 CI다.

## 실제 개발 연구 정보 복원 검증

AWS 내부에서 개발 DB를 읽기 전용으로 내보내고 별도 임시 DB에 복원했다. **이관 대상 11개 테이블의 전체 일반 컬럼 해시와 건수가 원본과 일치**했고, 원본 연구 정보는 바뀌지 않았다.

위 단과대 수는 소속별 집계이므로 복수 소속 연구실을 여러 단과대에서 셀 수 있다. 합계를 고유 연구실 622개와 같아야 한다고 해석하지 않는다.

개발 DB의 임시 후기는 **8건 그대로 보존**, 복원 대상 후기는 **0건**이다. 회원·인증 토큰·게시글·댓글·북마크·미승격 후보 등 제외 테이블 12개도 대상에서 0건임을 확인했다. 중복 이메일 삽입 실패 시 롤백과 사용자 활동이 있는 대상 거부를 검증했다. 검증용 임시 스키마는 제거했고 기존 개발 백엔드는 정상 상태를 확인했다.

스냅샷은 AWS 내부에만 보관했다. 로컬 원문 복사는 수행하지 않았고 실제 스냅샷 경로·DB 행·계정 정보는 문서에 포함하지 않는다. 이 건수는 10월 8일의 검증 결과이며 실제 이관 시 최신 export와 대조를 다시 해야 한다.

## 리뷰와 남은 작업

프로젝트의 Flyway 마이그레이션·단일책임 원칙 스킬을 적용해 검토했다. 기존 SQL·Java 마이그레이션은 수정하지 않았고, 애플리케이션 배포 교체와 최초 연구 정보 이관을 별도 도구로 분리했다. 이관의 읽기·검증·복원·명령 처리는 함수로 나뉜다. Java/Spring용 계층 규칙을 Python 도구에 기계적으로 추가할 근거는 없었다.

이 검증은 운영 이관 완료가 아니다. 다음 단계에서는 새 운영 DB를 준비하고, Pull 타이머와 대상 앱을 중지한 상태에서 동일 스키마·Flyway 이력을 확인한 뒤 최신 연구 정보를 복원해야 한다. 운영 API·FE·쿠키·로그인 기능 확인, 초기 백업·복원·정기 백업은 남아 있다.
