# SEBU 운영 모니터링 구축 기록 - 2026-10-10

**개발 환경에만 있던 Grafana 모니터링을 운영에도 연결하고, 운영 14개 패널과 `sebu-email` 장애 알림을 구성했다.** 기존 개발 대시보드는 개발 지표만 조회하도록 분리했다. 이 기록은 2026-10-10의 서버 점검·Grafana 저장 후 조회·쿼리 실행 결과를 정리한 것으로, 이후 시점의 실시간 상태를 보증하지 않는다.

## 변경한 범위

운영 백엔드는 `main`의 `3c7445e173528b22c40c9abb47b0fb35ad81ff6e` 이미지를 그대로 사용했다. 런타임 프로필을 `prod`에서 `prod,monitoring`으로 변경하고 전용 수집 인증을 설정했다. 애플리케이션 코드·DB 스키마·FE 구현을 바꾸지 않았다. AWS 작업은 프로젝트 `sebu`, 선택 리전 `ap-southeast-2`에서 진행했다.

| 항목 | 적용·확인 결과 |
|---|---|
| 운영 실행 설정 | 배포 잠금과 사전 DB 백업 후 동일 이미지로 백엔드 재생성. 이미지 digest·배포 revision 기록 유지 |
| 운영 보호 | 기존 컨테이너 메모리 제한·네트워크·로컬 포트·로그 제한 유지. MySQL·Caddy 설정 변경 없음 |
| 수집 인증 | 별도 Bearer 토큰 사용, 서버 파일 접근 제한. 비밀값·환경 파일·DB 원문은 지식 저장소에 포함하지 않음 |
| 수집 방식 | Grafana Cloud hosted Metrics Endpoint, `https://api.sebu.kr/actuator/prometheus`, 1분 간격 |
| 운영 대상 | `scrape_job="sebu-prod-backend"` |
| 운영 화면 | [SEBU Production Monitoring](https://niftyboxwood1620.grafana.net/d/sebu-prod-monitoring/sebu-production-monitoring), 14개 패널·16개 쿼리 |
| 개발 화면 | 기존 UID·제목·9개 패널 유지, 모든 쿼리를 `sebu-dev-backend`로 제한, 저장 후 version 14 확인 |
| 운영 장애 규칙 | [SEBU Production Backend Down](https://niftyboxwood1620.grafana.net/alerting/grafana/fg0ru41k2mwhsd/view), `environment=production`, 기존 `sebu-email` 연결 |
| 배포·백업 | Pull 배포 타이머 유지. 당일 03:00:24~03:00:26 KST 일일 백업 성공과 S3 검증 기록 확인 |

기존 개발 장애 규칙의 조회 대상·조건·연락처는 유지했다. 새 운영 규칙은 `min(up{scrape_job="sebu-prod-backend"}) or vector(0)`이 1 미만인 상태를 2분 대기 후 감지하도록 구성했다. 평가 주기는 1분이며, 데이터 없음·평가 오류도 `Alerting`으로 설정했다.

## 검증 결과

- 서버 재설정 도구의 모의 테스트 24개와 독립 검토를 통과하고, 변경 전 사전 점검을 실행했다. 실제 실행 뒤 동일 이미지 유지·컨테이너 정상 상태·readiness 성공을 확인했다.
- Prometheus 경로는 올바른 수집 인증으로 200, 무인증으로 401이었다. 실제 Grafana 연결 테스트와 수집 작업 저장을 성공시켰다.
- 운영의 16개 패널 쿼리가 모두 성공했고, 서버가 실제 노출하는 메트릭 이름과 대조했다. 운영 `up=1`, 장애 규칙 `Normal`을 확인했다.
- 연구실·게시글 공개 조회 API의 200 응답을 확인했다. 이후 연구실 p95에 실제 요청 집계값이 나타났다. 게시글처럼 충분한 요청 증가분이 없는 기간의 p95는 `N/A`일 수 있음을 확인했다.
- 개발 대시보드 저장 결과를 다시 읽어 모든 선택자가 개발 대상으로 제한됐는지 확인했다. 운영 추가 후 개발 지표와 합산되는 문제를 막았다.
- 실제 존재하는 운영 대상 쿼리는 1, 별도 존재하지 않는 검증용 이름의 조회는 fallback 0을 반환했다. 이는 쿼리 동작 확인이며 운영 서버 장애를 일으킨 실험은 아니다.

당시 운영 컨테이너의 메모리는 약 379 MiB / 768 MiB, 호스트 가용 메모리는 약 525 MiB였다. 이는 수집 활성화 직후 참고값이며 향후 부하나 메모리 여유를 보증하지 않는다. 대시보드의 JVM Heap 수치와 호스트 전체 가용 메모리를 혼동하지 않는다.

## 비용과 추가하지 않은 기능

당시 Grafana Cloud Free 플랜의 한도는 활성 메트릭 시계열 10,000개·14일 보존으로 확인했다. 최종 조회에서 개발 48개·운영 71개의 시계열을 확인했으며, 이 개수는 요청·상태 코드·지표 생성에 따라 바뀔 수 있다. 추가 EC2·서버 수집기·유료 모니터링 서비스를 만들거나 유료 플랜으로 전환하지 않았다. 기존 AWS 서버와 네트워크 비용은 별도다.

사용자 수 집계, EC2 전체 자원·MySQL 전체 지표, 외부 로그 전송, 백업 실패 알림과 자원별 임계치 알림은 추가하지 않았다. 이번 알림의 대상은 운영 지표 수집 실패다. CPU·메모리 지표는 백엔드 JVM 범위이고 HTTP 요청률을 접속자 수로 계산하지 않는다.

실제 테스트 메일 발송·고의 운영 장애 시험·학교 계정 로그인과 쓰기 기능 검증은 수행하지 않았다. 알림 규칙·연락처 연결·정상 상태 확인을 실제 이메일 도착 검증으로 확대하지 않는다.
