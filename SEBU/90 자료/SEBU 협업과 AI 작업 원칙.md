# SEBU 협업과 AI 작업 원칙

AI는 확인한 코드·실행 결과를 바탕으로 작업하고, 팀원은 SEBU-brain에서 최신 근거와 남은 일을 확인한다. 도구 연결 자체를 구현·배포 완료로 취급하지 않는다.

## 역할과 실행 범위

| 대상 | 이 프로젝트의 작업 방침 |
|---|---|
| 백엔드·문서 | 요청한 범위에서 코드 확인, 변경, 테스트, PR과 문서 갱신 진행 |
| 프론트엔드 | FE 담당자가 구현·배포. 별도 명시 없이 AI가 FE 수정·커밋·PR·머지하지 않음 |
| AWS | AWS Agent Toolkit·MCP와 관련 AWS 스킬 우선. 선택된 리전은 ap-southeast-2, CLI 프로필 이름은 sebu |
| 웹 브라우저 | Aside로 읽고 확인. 사용자에게 넘겨야 하면 접속 URL과 붙여 넣을 구체적인 프롬프트 제공 |
| 운영 단계 | 단계가 끝나면 결과·남은 조건을 브리핑하고 다음 진행 지시 대기 |
| 비용 | 무료 도구·Free Tier와 실제 크레딧을 우선 검토. 유료 전환·새 비용 선택을 무료 설정에 포함하지 않음 |

AWS에서는 계정 대신 프로젝트라는 용어를 사용한다. MCP 접속 리전이 보이더라도 실제 리소스 배포 리전과 혼동하지 않는다. 접속·권한·플랜은 작업 시점에 확인하며 과거 연결 성공을 현재 사용 가능의 보증으로 삼지 않는다.

## 질문과 지식 갱신 요청

프로젝트 질문은 이 보관함의 관련 노트와 근거 코드로 답한다. 현재 운영 상태가 핵심이면 저장소의 기본 설정만 읽고 단정하지 않고, 배포 커밋·실행 증거를 확인한다.

예시 요청:

```text
최신 main/develop과 FE dev 변경을 확인해서 관련 세컨 브레인 문서를 업데이트해줘.
현재 구현, 운영에서 확인한 결과, 아직 제안인 내용을 구분해줘.
```

코드 머지 후 AI가 자동으로 문서를 갱신하는 상시 작업은 설정하지 않았다. 로컬 앱의 주기 실행 방식은 논의했지만 사용자가 진행하지 않기로 했다. 현재는 요청 → 변경 확인 → 문서 수정·검사 → 문서 PR → 팀원 Pull 흐름이다.

## 노션 API 명세 검토

`sebu-notion-api-review` 스킬이 설치된 환경에서는 다음처럼 요청할 수 있다.

```text
$sebu-notion-api-review [노션 링크]
요청·응답이 명확하게 작성됐는지 검토하고 실제 코드와 비교해줘.
```

검토에서는 메서드·경로, Path/Query/Header/Cookie/Body, 필수·선택·null, 성공·실패 응답과 JSON 예시를 확인한다. FE가 실제로 구성할 요청과 처리할 응답이 드러나도록 쓴다. 문서가 현재 계약인지 합의안인지 초안인지 먼저 구분한다.

읽기·검토 요청과 노션 수정 요청은 다르다. 페이지 수정이 필요하면 대상과 수정 범위를 함께 요청한다. 이 스킬은 개인 도구 환경에 설치된 것이며, 브레인 저장소를 Pull하는 것만으로 다른 팀원에게 자동 설치되지 않는다. 현재 웹 확인은 Aside 사용 방침을 따른다.

## 리뷰와 완료 보고

- DB 변경은 기존 적용 이력·환경별 차이·안정적인 ID를 검토하고 새 마이그레이션으로 반영한다.
- 단일 책임 원칙은 클래스 수를 늘리는 규칙이 아니다. 변경 이유와 역할 경계가 분리됐는지 검토한다.
- 리뷰는 사용자가 요청한 형식을 우선한다. 별도 형식이 없으면 결론 → 문제 상황과 근거 → 해결 방식 순서로 짧게 설명한다.
- 코드 확인, 테스트 통과, PR 머지, 이미지 게시, 서버 적용, 사용자 기능 검증을 구분한다.
- 인증 정보·토큰·실제 환경 파일·DB 백업을 노트에 넣지 않는다. 예시는 비밀값 없이 재현 가능한 절차로 남긴다.
