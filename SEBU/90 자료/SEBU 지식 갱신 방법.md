# SEBU 지식 갱신 방법

코드 변경을 Git 기준으로 비교하고, 노트를 검토한 뒤 새 기준을 기록한다. 도구는 의미를 자동 해석하거나 문장을 자동으로 갱신하지 않는다.

## 준비

문서를 읽는 데 Node.js나 코드 레포는 필요하지 않다. 갱신 도구는 Node.js 20 이상과 Git을 사용하며 별도 npm 패키지 설치가 필요 없다.

레포 루트에서 sources.example.json을 sources.local.json으로 복사하고 각 코드 레포의 경로와 비교할 ref를 설정한다. 상대 경로는 SEBU-brain 루트를 기준으로 한다. 이 개인 파일은 커밋하지 않는다.

## 변경 확인

코드 레포에서 git fetch origin으로 원격 정보를 갱신한 뒤 문서 레포에서 실행한다.

```sh
npm run sources:check
```

기록한 기준 커밋과 설정 ref의 차이를 비교한다. 등록된 근거뿐 아니라 새 파일·삭제·이름 변경도 확인하고, 이미 연결된 노트와 아직 연결되지 않은 변경을 표시한다. 로컬 미커밋 변경은 별도로 표시하며 기준에 자동 포함하지 않는다.

도구는 네트워크 fetch를 수행하지 않는다. 기준 커밋을 로컬에서 찾지 못하면 안내에 따라 해당 커밋을 가져온다. 완전한 clone을 사용하면 이전 기준을 비교하기 편하다.

## 검토 후 기준 갱신

1. 코드와 관련 노트를 읽고 설명·현황·제안을 고친다.
2. 새 출처는 노트 frontmatter의 source_ids에 B:또는 F:저장소상대경로로 추가한다.
3. 구현을 확인한 노트의 verified 날짜와 상태를 갱신한다.
4. [[SEBU 저장소와 기준 버전]] 표, 변경 기록과 미완료 과제도 수정한다.
   운영 이력이 바뀌었으면 BE main 배포 커밋과 실행 확인 시각도 별도로 남긴다. B=develop의 해시만으로 운영 버전을 추정하지 않는다. FE는 이 팀에서 dev가 운영 브랜치다.
5. 검토를 마쳤을 때만 아래 명령으로 커밋·파일 해시와 자동 근거 링크를 갱신한다.

```sh
npm run sources:record -- --reviewed
npm run check
npm test
```

source_ids에 남은 파일이 기준 ref에서 삭제됐다면 기록이 실패한다. 출처를 새 경로로 옮기거나 노트에서 제거한 뒤 다시 실행한다. sources:record는 문장 자체나 verified 날짜를 자동 수정하지 않는다.

날짜가 붙은 과거 기록과 이전한 원문은 그 시점의 상태를 보존한다. 현재 현황·홈·지도·검토 목록을 갱신하고, 과거 기록에는 새 완료 기록으로 가는 안내를 붙인다. 배포 준비 완료를 배포 완료로, 공개 API 200을 로그인·작성 성공으로 바꾸지 않는다.

## 종료 코드와 한계

- sources:check: 차이 없음 0, 검토할 변경 1, 설정·Git 확인 실패 2.
- npm run check: 문서 구조·링크·출처 기준 검사가 통과하면 0, 실패하면 1.
- 의미 검증, 서버 배포 상태, 학교 계정 로그인 검증은 별도다.
- GitHub 근거 링크는 기록된 커밋에 고정되어 있다. 브랜치가 움직여도 해당 설명의 근거를 추적할 수 있다.
