# SEBU AI 수집 요약 매핑 설계

Spring이 기사를 수집하고 외부 Gemini API로 요약·관련 분야를 받는다. 백엔드가 응답과 분야 ID를 검증한 뒤 실제 DB의 연구실을 연결하고 저장한다. **기사 조회 시에는 저장한 결과를 재사용**한다. 아래는 제공 기획서의 설계 계획이며 현재 배포된 처리 흐름을 설명하는 문서가 아니다.

![기획서의 서비스 구성도](<assets/service-architecture.png>)

## 1. 기사 수집과 입력 준비

- 초기에는 수동 실행으로 결과를 확인하고 이후 Spring `@Scheduled`로 수집한다. 주기와 건수는 운영 부하·API 한도를 확인한 뒤 정한다.
- jsoup으로 허용된 HTML에서 제목·본문·저자·발행일·원문 URL을 추출한다. 메뉴와 광고를 제거한 텍스트를 AI에 전달한다.
- 기사 URL의 DB 고유 제약으로 중복 처리를 막는 계획이다.
- 군사·보안·AI·건강·의료 기술·바이러스 등 폭넓은 기사를 다루되 정치적 주장이나 정당·선거 중심 글은 제외한다.

기획서는 360info 자체 기사의 CC BY 4.0 조건을 수집 근거로 제시한다. 실제 수집 대상은 이용 조건을 확인한 기사로 제한하며, 저자·제목·매체·원문 링크·라이선스 링크·AI 요약 및 번역 사실을 표시한다. 사진은 별도 권리를 확인하고 불명확하면 직접 만든 기본 이미지를 사용한다. 이는 원문의 이용 계획 정리이며 이번 작업에서 개별 기사 이용 허가나 현행 약관을 새로 검증한 것은 아니다.

## 2. Gemini 요청과 응답

| 구분 | 원문에서 정한 내용 |
|---|---|
| 입력 | 기사 제목·정리된 본문, DB 연구 분야의 ID·분야명 및 검토한 설명·동의어 후보 목록 |
| 요청 | 본문에 있는 사실만 한국어 세 문장으로 요약하고 후보 목록에서 관련 분야를 선택 |
| 출력 | 요약, 연구 키워드, 관련 연구 분야 ID, 연결 이유를 JSON으로 반환 |
| 형식 제한 | JSON Schema 지정, Jackson으로 DTO 역직렬화 |
| 백엔드 검증 | 필수값·세 문장 여부·분야 ID 존재 여부 확인 |
| 내용 검수 | 초기 기사 10~20건을 원문과 대조해 사실 오류·의미 왜곡 확인 |

Schema를 만족하는 응답도 사실이 정확하다고 보장하지 않는다. 정확한 JSON 필드명·자료형·오류 응답·엔드포인트는 아직 정하지 않았으므로 이 표를 완성된 API 계약으로 사용하지 않는다. 모델은 무료 티어 후보로 시작하되 품질·호출 한도를 확인하고 설정값으로 교체할 수 있게 한다는 계획이며, 모델명과 영구 무료 사용은 확정하지 않았다.

## 3. 연구 분야에서 연구실로 연결

1. 기존 `research_field`의 ID·분야명에 검토한 설명과 동의어를 붙여 후보 목록을 준비한다.
2. AI가 후보 안에서 관련 ID와 연결 이유를 반환한다.
3. Spring이 ID가 실제로 존재하는지 검증한다.
4. `laboratory_research_field`에서 해당 분야와 연결된 연구실을 조회한다.
5. 교수명·연구실 URL은 DB 값을 사용하고, 근거가 없으면 연결 결과를 비워 둔다.

AI가 만든 키워드 문자열을 연구실 이름과 바로 비교하지 않는다. 연구 분야 ID와 화면 그룹을 위한 카테고리 ID는 구분한다. 기존 분류 체계와의 관계는 [[SEBU 연구 분야 분류]]와 [[SEBU 데이터 모델]]을 참고한다.

## 4. 저장과 화면 제공

검증한 요약·분야 연결 결과와 출처를 MySQL에 저장한다. React 화면은 Spring 조회 API를 통해 저장 결과를 기사 카드로 표시하고 연구실 상세 정보와 후기로 연결한다. 같은 기사를 다시 열 때 AI를 다시 호출하지 않는 방향이다. 저장 테이블·마이그레이션과 갱신 정책은 후속 설계에서 확정한다.

## 5. 서버 부하와 실패 처리

기획서에는 2026-10-12 12:33 KST 운영 서버가 t3.small, RAM 2 GiB, 가용 메모리 약 489 MiB였다고 기록돼 있다. 이는 과거 측정값으로 현재 용량 여유를 증명하지 않는다.

계획은 EC2 안에 모델을 설치하지 않고 외부 Gemini API를 호출하는 것이다. 브라우저를 실행하지 않고 HTML을 읽으며 기사를 한 건씩 처리한다. 본문 크기와 요청 시간을 제한하고, 429 응답에는 대기 후 제한된 횟수만 재시도한다. 실패 기록·수집 주기 조정·결과 재사용으로 중복 작업과 부하를 줄인다.

개발 서버에서 메모리와 기존 API 응답 시간을 측정한 뒤 운영 반영을 판단한다. 구체적인 크기·시간·재시도 횟수·호출량 상한은 미정이다.
